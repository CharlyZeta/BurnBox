# CONTRACT: Eventos y auditoría mínima: puerto de publicación, contexto de request y logs estructurados
# ID: FEAT-0003
# Status: DRAFT
# Mode: GATE
# Gate-Mode: STRICT

## Intent
Implementar el puerto desacoplado de publicación de eventos de seguridad con Spring Modulith, contexto de request con Scoped Values de Java 25, registro simple de eventos en base de datos y logging estructurado en JSON con filtro de seguridad y test canario.

## User Story
- Como: **Desarrollador**
- Quiero: **registrar eventos de seguridad y propagar contexto de request sin estado global**
- Para: **auditar operaciones sensibles y asegurar observabilidad sin filtrar secretos ni PII**

## Depends On
- FEAT-0001

## Use Case
**Actor:** Módulos de aplicación
**Goal:** Publicar eventos de seguridad, capturar request_id/actor en Scoped Values y registrar logs limpios

### Main Flow
1. Solicitud HTTP entrante es interceptada; se genera `request_id` único y se asocia en un `ScopedValue` junto con el actor y prefijo de IP
2. Módulo de dominio emite un record de evento de seguridad al puerto `SecurityEventPublisher`
3. Módulo `audit` consume el evento y persiste una fila en `security_event` con `event_type`, `occurred_at`, `actor_user_id`, `request_id`, `ip_hash` y `details` (jsonb)
4. Appender de logging serializa mensajes en formato JSON estructurado incluyendo `timestamp`, `level`, `request_id`, `user_ref` y `event`
5. Solicitud culmina y el ámbito del Scoped Value se limpia automáticamente

### Alternative Flows
- AF-01: Petición anónima asigna actor nulo y calcula `ip_hash` mediante HMAC con sal derivada de `BURNBOX_IP_HASH_SALT`
- AF-02: Evento recibido sin detalles adicionales persiste `details` como objeto JSON vacío `{}`
- AF-03: Evento fallido en persistencia registra error en log técnico sin interrumpir el flujo del emisor

## Business Rules
- BR-001: **Puerto de eventos desacoplado** — los módulos emisores publican a través de una interfaz de puerto; solo `audit` y `notification` consumen eventos
- BR-002: **Contexto con Scoped Values** — `request_id` y actor viajan en `ScopedValue` de Java 25 ligado al request; prohibido el uso de `ThreadLocal` manual
- BR-003: **Estructura estricta de logs JSON** — los logs contienen timestamp, level, request_id, user_ref (id opaco) y event; prohibido texto plano desestructurado
- BR-004: **Cero secretos en logs** — nunca se registran tokens en claro, contenido, passphrases, ciphertext ni cabeceras `Cookie` o `Authorization`
- BR-005: **Enmascaramiento de tokens** — en caso de registrar referencia a un token, se permiten únicamente los primeros 8 caracteres de su hash SHA-256
- BR-006: **Cero PII ni secretos en auditoría** — el campo `security_event.details` no almacena contraseñas, contenido de secretos ni información personal identificable
- BR-007: **Test canario en CI** — el pipeline ejecuta un test canario que falla el build si cualquier patrón de secreto aparece en los logs

## Acceptance Criteria
- AC-001: GIVEN request entrante WHEN interceptor se ejecuta THEN genera UUID en `request_id` accesible vía Scoped Value durante todo el request
- AC-002: GIVEN actor autenticado o anónimo WHEN se consulta el contexto THEN devuelve la identidad opaca o vacío según corresponda
- AC-003: GIVEN un evento publicado WHEN `SecurityEventPublisher.publish()` es invocado THEN persiste fila en tabla `security_event` con tipo y fecha
- AC-004: GIVEN evento de seguridad WHEN se guarda en base de datos THEN `ip_hash` es un HMAC no reversible y `details` no contiene texto en claro
- AC-005: GIVEN registro de log WHEN se serializa a JSON THEN contiene `request_id`, `level`, `timestamp` y `event` válidos
- AC-006: GIVEN traza de log generada con un secreto WHEN test canario escanea THEN detecta la presencia y falla el test
- AC-007: GIVEN log de operación con token WHEN se escribe en log THEN solo expone los primeros 8 caracteres del hash SHA-256
- AC-008: GIVEN test de integración `@ApplicationModuleTest` WHEN emite evento de dominio THEN el consumidor en `audit` lo procesa exitosamente
