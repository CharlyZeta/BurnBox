## Intent
Implementar la autenticación federada OIDC para el proveedor Microsoft (Entra ID) en el módulo `identity`: soporte para endpoint multi-tenant (`common`), validador dinámico de issuer por tenant `https://login.microsoftonline.com/{tid}/v2.0` alineado con el claim `tid`, verificación estricta de `email_verified` para prevenir vulnerabilidades de nOAuth / toma de cuentas pre-existentes, y vinculación idempotente al esquema relacional `linked_identity`.

## User Story
- Como: **Usuario que dispone de una cuenta de Microsoft corporativa o personal**
- Quiero: **iniciar sesión en Burnbox mediante Microsoft Entra ID OIDC de forma segura**
- Para: **acceder al servicio validando dinámicamente el tenant y garantizando que cuentas no verificadas no vulneren identidades existentes**

## Depends On
- FEAT-0001, FEAT-0003, FEAT-0009

## Use Case
**Actor:** Visitante / Usuario de Microsoft
**Goal:** Iniciar sesión con Microsoft OIDC validando dinámicamente el issuer y aprovisionando la identidad bajo política nOAuth

### Main Flow
1. El usuario hace clic en "Continuar con Microsoft" en `/login`
2. El sistema redirige al endpoint de autorización de Microsoft Entra ID (`/common/oauth2/v2.0/authorize`) con PKCE
3. Microsoft autentica al usuario y devuelve el authorization code a `/login/oauth2/code/microsoft`
4. El decodificador valida dinámicamente que el issuer cumple el patrón `https://login.microsoftonline.com/{tid}/v2.0` y coincide con el claim `tid`
5. `BurnboxOidcUserService` extrae los claims con proveedor `MICROSOFT`, `issuer` y `subject`
6. `UserProvisioningService` comprueba `(issuer, sub)` y el flag `email_verified`
7. El usuario es aprovisionado o autenticado según su estado y redirigido a `/`

### Alternative Flows
- AF-01: Si el token de Microsoft presenta un issuer con formato inválido o que no coincide con el claim `tid`, la validación falla y se rechaza la autenticación
- AF-02: Si la cuenta de Microsoft no cuenta con `email_verified == true`, el usuario se aprovisiona con `emailVerified = false` y no puede colisionar ni vincularse con cuentas verificadas
- AF-03: Si un usuario con cuenta Microsoft previamente registrada se encuentra en estado `DISABLED`, se rechaza el acceso emitiendo `LoginRejected`
- AF-04: Si el email verificado de la cuenta Microsoft colisiona con el email verificado de otra cuenta preexistente, se rechaza la fusión automática (mitigación nOAuth)

## Business Rules
- BR-001: Validación dinámica de issuer Microsoft — el issuer debe coincidir con `^https://login\.microsoftonline\.com/([a-fA-F0-9\-]{36})/v2\.0$` y ser idéntico al claim `tid`
- BR-002: Invariante nOAuth para Microsoft — claims de Microsoft sin `email_verified == true` explícito se registran como no verificados y tienen prohibida la fusión con identidades existentes
- BR-003: Tupla de identidad unívoca — la identidad Microsoft se define exclusivamente por `(issuer, sub)` donde issuer incluye el `tid` del inquilino
- BR-004: Control de estados de usuario — usuarios Microsoft `ACTIVE` acceden normalmente, `DISABLED` son rechazados y `PENDING_DELETION` acceden con advertencia
- BR-005: Eventos de dominio y auditoría — emisión de eventos `UserRegistered`, `UserLoggedIn` o `LoginRejected` sin PII en logs ni almacenamiento de tokens

## Acceptance Criteria
- AC-001: Login con Microsoft mediante id_token con issuer válido de tenant autentica exitosamente
- AC-002: Validador de issuer rechaza tokens cuyo issuer no coincida con el claim tid o viole el formato esperado
- AC-003: Token de Microsoft sin email_verified o con email_verified false no valida el email en el sistema
- AC-004: Colisión de email verificado de Microsoft con usuario existente bloquea la fusión automática
- AC-005: Usuario Microsoft existente actualiza last_login_at y last_used_at en linked_identity
- AC-006: Usuario Microsoft en estado DISABLED es rechazado emitiendo LoginRejected
