## Intent
Implementar el módulo criptográfico puro: generación de tokens opacos de 32 bytes con hash SHA-256, cifrado envelope AES-256-GCM con AAD por secreto, interfaz KeyProvider con adaptador local para KEK y key ring con una versión activa.

## User Story
- Como: **Desarrollador**
- Quiero: **proveer servicios criptográficos encapsulados en el módulo crypto**
- Para: **asegurar confidencialidad e integridad sin exponer primitivas de cifrado al resto de la aplicación**

## Depends On
- FEAT-0001

## Use Case
**Actor:** Módulo secret (consumidor interno)
**Goal:** Generar tokens, derivar hash de almacenamiento, cifrar contenido con DEK y envolver DEK con KEK

### Main Flow
1. `CryptoTokenService.generateToken()` produce 32 bytes con SecureRandom en base64url sin padding (43 caracteres)
2. `CryptoTokenService.hashToken(token)` calcula el hash SHA-256 para persistencia e indexación
3. `SecretEnvelopeService.encrypt(plaintext, secretId, keyVersion)` genera DEK de 256 bits y cifra con AES-256-GCM con nonce aleatorio de 96 bits
4. La encriptación vincula AAD = `secretId || keyVersion || formatVersion` y produce un tag de autenticación de 128 bits
5. `KeyProvider.wrap(dek, keyVersion)` envuelve la DEK con la KEK activa correspondiente
6. `SecretEnvelopeService.decrypt(envelope, secretId)` desenvuelve la DEK y descifra el texto validando AAD y tag GCM

### Alternative Flows
- AF-01: Intento de descifrado con AAD alterado (otro secretId o versión) falla inmediatamente por excepción criptográfica de autenticación
- AF-02: Intento de descifrado con ciphertext o tag manipulado (tampering) es rechazado por AES-GCM
- AF-03: `KeyProvider.wrap` o `unwrap` con una versión de KEK no existente o en estado RETIRED genera error explícito
- AF-04: Adaptador local de `KeyProvider` inicializa KEK de 256 bits desde variable de entorno `BURNBOX_KEK_V1`

## Business Rules
- BR-001: **Aislamiento criptográfico total** — todo el código que use `javax.crypto` reside estrictamente dentro de `crypto`; ArchUnit prohíbe importarlo en otros paquetes
- BR-002: **Token opaco de alta entropía** — 32 bytes aleatorios (`SecureRandom`), codificados en base64url sin relleno (43 caracteres)
- BR-003: **Persistencia exclusiva del hash** — la base de datos almacena únicamente el hash SHA-256 del token; el token original nunca se persiste ni se recupera
- BR-004: **Cifrado envelope AES-256-GCM** — cada secreto genera su propia DEK de 256 bits, nonce de 96 bits y tag de autenticación de 128 bits
- BR-005: **Enlace de contexto con AAD** — todo cifrado incluye AAD formado por `id_secreto || version_clave || version_formato` para evitar reubicación de datos
- BR-006: **Gestión del Key Ring** — `key_version` mantiene exactamente una clave en estado ACTIVE; las anteriores quedan en DECRYPT_ONLY o RETIRED
- BR-007: **KeyProvider local (MVP)** — implementación desacoplada detrás de interfaz que lee KEK de 256 bits desde variables de entorno o archivo montado

## Acceptance Criteria
- AC-001: GIVEN solicitud de token WHEN `generateToken()` se invoca THEN devuelve string de 43 caracteres en base64url con 256 bits de entropía
- AC-002: GIVEN un token en claro WHEN `hashToken(token)` se ejecuta THEN genera hash SHA-256 de 32 bytes en formato hexadecimal consistente
- AC-003: GIVEN texto plano de hasta 64 KiB y metadatos de secreto WHEN se cifra THEN produce ciphertext, nonce de 96 bits, tag de 128 bits y DEK envuelta
- AC-004: GIVEN paquete cifrado legítimo WHEN se descifra con la misma clave y AAD THEN recupera exactamente el texto plano original
- AC-005: GIVEN paquete cifrado WHEN se intenta descifrar alterando el secretId del AAD THEN falla la verificación de autenticidad
- AC-006: GIVEN paquete cifrado WHEN se manipula un solo bit del ciphertext o tag THEN el descifrado falla con AEADBadTagException
- AC-007: GIVEN DEK válida WHEN `wrap` y `unwrap` se ejecutan con KEK activa THEN la DEK recuperada es idéntica a la original
- AC-008: GIVEN regla ArchUnit de CI WHEN analiza paquetes fuera de `crypto` THEN confirma cero importaciones de `javax.crypto`
