## Intent
Implementar la capacidad de restringir el acceso a un secreto exclusivamente a un destinatario autenticado con email verificado (E4/C-14), validando el campo opcional recipient_email al crear el secreto, exigiendo autenticación OIDC previa al revelar en GET /s/{token}, verificando que el email del usuario autenticado esté marcado como verificado y coincida con el destinatario indicado, y preservando indistinguibilidad para terceros no autorizados mediante respuesta uniforme NotAvailable.

## User Story
- Como: **Usuario autenticado**
- Quiero: **restringir el acceso a un secreto a un email destinatario verificado**
- Para: **garantizar que únicamente el propietario legítimo de dicha casilla de correo pueda revelar su contenido**

## Use Case
**Actor:** Creador autenticado y Destinatario
**Goal:** Restringir y acceder a un secreto ligado a un email destinatario

### Main Flow
1. El creador autenticado envía POST /secrets con contenido, recipientEmail válido, vencimiento y opcionalmente passphrase.
2. El sistema valida el formato de recipientEmail, cifra el payload y persiste el secreto con recipient_email configurado.
3. El destinatario anónimo accede a GET /s/{token}; el sistema detecta que el secreto es restringido y responde requiriendo inicio de sesión OIDC sin revelar datos.
4. El destinatario inicia sesión con su proveedor OIDC obteniendo email_verified en true coincidente con recipient_email.
5. El destinatario autenticado accede a GET /s/{token}; el sistema verifica la correspondencia de email y presenta la pantalla intermedia de revelado.
6. El destinatario envía POST /s/{token}/reveal; el sistema valida la autorización, consume el secreto atómicamente y devuelve el texto plano.

### Alternative Flows
- AF-01: Creación con formato de email inválido es rechazada con error de validación HTTP 400 sin persistir el secreto.
- AF-02: Destinatario anónimo envía POST /s/{token}/reveal directamente; el sistema rechaza la solicitud exigiendo autenticación.
- AF-03: Usuario autenticado con email no coincidente o no verificado intenta acceder a GET o POST /s/{token}/reveal; el sistema devuelve respuesta genérica uniforme NotAvailable.
- AF-04: Secreto restringido ya consumido, expirado o destruido responde con respuesta genérica uniforme NotAvailable.

## Business Rules
- BR-001: **Formato válido de email de destinatario** — Si se suministra recipient_email, debe cumplir con un formato de email válido (RFC 5322 simplificado, con @ y dominio, longitud máxima de 255 caracteres).
- BR-002: **Requisito de autenticación estricta** — Un secreto con recipient_email configurado no puede ser revelado por usuarios anónimos ni por usuarios autenticados sin email verificado (email_verified == true).
- BR-003: **Coincidencia unívoca de email** — El email verificado del usuario autenticado debe coincidir de manera insensible a mayúsculas y minúsculas con el recipient_email persistido en el secreto.
- BR-004: **Indistinguibilidad y anti-enumeración** — Si un usuario autenticado cuyo email no coincide accede a un secreto restringido, el sistema responde con la misma vista genérica y código HTTP que un secreto inexistente, sin confirmar la existencia del secreto ni revelar la dirección configurada.
- BR-005: **Composición con Passphrase (E3 + E4)** — Un secreto con destinatario restringido puede opcionalmente protegerse con passphrase; la validación de identidad del destinatario precede a la solicitud y evaluación de la contraseña.
- BR-006: **Auditoría sin filtración de PII** — Si ocurre un intento de acceso no autorizado a un secreto restringido, se emite el evento SecretAccessDenied registrando el hash truncado del secreto y el ID de usuario si existe, sin registrar la dirección de email del destinatario en los detalles del evento.

## Acceptance Criteria
- AC-001: GIVEN creador autenticado WHEN envía POST /secrets con email destinatario válido THEN el secreto se guarda con recipient_email normalizado y devuelve link único.
- AC-002: GIVEN formulario de creación WHEN se envía email sintácticamente inválido THEN devuelve error de validación y no persiste nada.
- AC-003: GIVEN secreto con destinatario WHEN visitante anónimo accede a GET /s/{token} THEN la respuesta requiere login sin consumir el secreto.
- AC-004: GIVEN secreto con destinatario WHEN usuario autenticado con email coincidente y verificado accede a GET /s/{token} THEN muestra botón para confirmar revelado.
- AC-005: GIVEN secreto con destinatario WHEN usuario autenticado con email diferente accede a GET /s/{token} THEN recibe respuesta uniforme NotAvailable.
- AC-006: GIVEN secreto con destinatario WHEN usuario autenticado con email coincidente ejecuta POST /s/{token}/reveal THEN el secreto se revela y consume exitosamente.
- AC-007: GIVEN secreto con destinatario y passphrase WHEN usuario autenticado con email coincidente envía passphrase correcta THEN el secreto se revela; con passphrase incorrecta disminuyen los intentos restantes.
- AC-008: GIVEN intento de revelado POST con usuario no coincidente WHEN se evalúa el acceso THEN emite evento de auditoría SecretAccessDenied sin incluir PII en los detalles.
