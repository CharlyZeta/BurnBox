## Intent
Implementar la interfaz web SSR en Thymeleaf para el revelado anónimo de secretos: página intermedia informativa GET /s/{token} que previene quemado por crawlers, formulario POST /s/{token}/reveal con protección CSRF por doble envío (sin sesión), renderizado directo sin Post/Redirect/Get, cabeceras anti-caché y respuesta uniforme indistinguible para recursos no disponibles.

## User Story
- Como: **Visitante anónimo**
- Quiero: **revelar el contenido de un link de secreto de un solo uso**
- Para: **acceder a la información confidencial de forma segura y sin dejar copias en la web**

## Depends On
- FEAT-0004

## Use Case
**Actor:** Visitante anónimo (destinatario del link)
**Goal:** Acceder al contenido de un secreto activo mediante su link único de forma segura

### Main Flow
1. Destinatario realiza `GET /s/{token}` y recibe la página intermedia informativa con botón "Revelar secreto"
2. La respuesta establece una cookie de CSRF con ámbito `/s/` y valor aleatorio para el mecanismo de doble envío
3. El usuario pulsa "Revelar secreto" y envía `POST /s/{token}/reveal` con el token CSRF en campo de formulario oculto
4. El controlador valida el token CSRF por doble envío y deriva el hash SHA-256 del token de la URL
5. Invoca a `SecretService.consumeSecret(tokenHash)` dentro del módulo de secreto
6. El controlador recibe el resultado sellado y renderiza directamente la vista de éxito con el contenido en bloque `<pre>`
7. La respuesta HTTP incluye `Cache-Control: no-store` y `X-Robots-Tag: noindex, nofollow`

### Alternative Flows
- AF-01: Petición `GET /s/{token}` generada por crawlers, antivirus o previsualizadores de chat (Slack, Teams) renderiza la vista intermedia y jamás incrementa las visualizaciones ni consume el secreto
- AF-02: `POST /s/{token}/reveal` con token CSRF ausente o discordante con la cookie es rechazado inmediatamente sin consumir el secreto
- AF-03: `POST /s/{token}/reveal` sobre un secreto inexistente, expirado o ya consumido devuelve respuesta uniforme de no disponible con código HTTP 200 y mensaje idéntico
- AF-04: Contenido renderizado escapa caracteres especiales vía `th:text` para mitigar ataques XSS y ofrece botón de copia al portapapeles
- AF-05: El switch sobre `RevealResult` mapea exhaustivamente todos los tipos de resultado definidos en el dominio

## Business Rules
- BR-001: **GET intermedio inocuo** — `GET /s/{token}` nunca altera el estado del secreto ni incrementa sus lecturas; está diseñado para neutralizar crawlers y previsualizadores
- BR-002: **Consumo exclusivo por POST** — el secreto solo se revela y consume mediante una petición `POST /s/{token}/reveal`
- BR-003: **CSRF anónimo por doble envío** — al no haber sesión de usuario, el POST anónimo valida que el token CSRF del formulario coincida con el valor de la cookie de ámbito `/s/` con `SameSite=Strict`
- BR-004: **Renderizado directo sin PRG** — el contenido revelado se renderiza directamente en la respuesta del POST; no se usa Post/Redirect/Get para evitar persistencia temporal en sesión o servidor
- BR-005: **Indistinguibilidad estricta de no disponibilidad** — cualquier secreto inexistente, vencido, consumido o destruido devuelve exactamente el mismo código HTTP, layout y mensaje genérico
- BR-006: **Cabeceras de no almacenamiento y no indexación** — toda respuesta bajo `/s/**` incluye estrictamente `Cache-Control: no-store` y `X-Robots-Tag: noindex, nofollow`
- BR-007: **Visualización segura sin utext** — el contenido del secreto se presenta exclusivamente dentro de etiquetas `<pre>` mediante `th:text`; `th:utext` queda terminantemente prohibido

## Acceptance Criteria
- AC-001: GIVEN secreto activo WHEN cliente envía `GET /s/{token}` THEN responde 200 con vista intermedia informativa y las visualizaciones en base permanecen en 0
- AC-002: GIVEN vista intermedia WHEN se renderiza THEN incluye cookie CSRF con `SameSite=Strict` y campo hidden en el formulario con valor coincidente
- AC-003: GIVEN formulario enviado WHEN `POST /s/{token}/reveal` con CSRF válido se procesa THEN responde 200 con el texto plano y el secreto pasa a consumido
- AC-004: GIVEN petición de revelado WHEN token CSRF es inválido o no coincide THEN rechaza la petición con 403 y no consume el secreto
- AC-005: GIVEN cuatro peticiones sobre secretos (inexistente, vencido, consumido y destruido) WHEN se envía POST de revelado THEN las cuatro respuestas son byte a byte idénticas en cuerpo y cabeceras
- AC-006: GIVEN cualquier respuesta bajo `/s/**` WHEN se analizan cabeceras HTTP THEN contiene `Cache-Control: no-store` y `X-Robots-Tag: noindex, nofollow`
- AC-007: GIVEN secreto con contenido que incluye código HTML/JavaScript `<script>alert(1)</script>` WHEN se renderiza THEN los tags aparecen escapados como texto literal sin ejecutarse
- AC-008: GIVEN controlador web WHEN evalúa `RevealResult` THEN implementa un pattern matching switch exhaustivo que cubre todos los subtipos de la interfaz sellada
