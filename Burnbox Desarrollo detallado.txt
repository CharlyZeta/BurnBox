Burnbox - Desarrollo detallado del proyecto
8 nov 2026 · @Gerardo Maidana
1. Visión, alcance y principios
Burnbox es una app web renderizada en servidor para compartir secretos (contraseñas, tokens, claves) mediante links de un solo uso que se destruyen al leerse o al vencer. El proyecto existe para demostrar, en un dominio chico y fácil de explicar, un stack de seguridad completo sobre Java 25 y Spring Boot 4. El nombre es provisional.
Qué demuestra en el portfolio
• Login con cuentas de Google y Microsoft (OIDC con PKCE), incluido el caso multi-tenant de Microsoft y una política de vinculación de cuentas que evita nOAuth.
• Sesiones server-side con gestión visible (listar y revocar) y cookies endurecidas.
• Passkeys (WebAuthn) como segundo factor y step-up para acciones sensibles.
• Criptografía aplicada: cifrado envelope con AES-GCM, rotación de claves y destrucción de datos.
• Consumo exactamente-una-vez bajo concurrencia.
• Auditoría con cadena de hashes verificable.
• Trabajo de fondo: jobs idempotentes, eventos durables y notificaciones.
• Java moderno (records, sealed, pattern matching, Scoped Values, virtual threads) con Spring Boot 4, Security 7 y Modulith.
Alcance del MVP
Secretos de texto de hasta 64 KiB, creados solo por usuarios autenticados y leídos por cualquiera que tenga el link. La lectura puede exigir una passphrase o estar restringida a un destinatario autenticado. El dueño ve estado, lecturas y vencimiento de sus secretos, nunca el contenido ni el link.
Fuera de alcance del MVP
Archivos adjuntos, cifrado zero-knowledge del lado del cliente, API pública y CLI, organizaciones, cobros, app móvil y login con password propio. Las extensiones viables están en la sección 16.
Principios que todo contrato debe respetar
1. Sin passwords propios: la identidad viene solo de OIDC y la app no guarda credenciales de usuario.
2. Corrección sin jobs: expiración y consumo se aplican en la lectura; los jobs son higiene y no condicionan la corrección.
3. Defensa en profundidad: cada protección tiene una segunda capa (token no adivinable, rate limiting y cifrado).
4. Indistinguible para anónimos: un link inexistente, vencido o consumido produce la misma respuesta.
5. Sin PII ni secretos en logs ni en auditoría.
6. Todo el tiempo pasa por un Clock inyectado; no hay Instant.now() suelto.
7. Cada comportamiento se prueba con el test más chico posible (sección 11).

3. Arquitectura y decisiones de stack
Burnbox es un monolito modular con Spring Modulith sobre Java 25 y Spring Boot 4, con PostgreSQL como único estado y render en servidor con Thymeleaf y htmx. Los módulos se hablan por eventos de dominio, de modo que quien emite no conoce a quien consume.
Los módulos de negocio publican eventos y solo audit y notification los consumen; PostgreSQL es el único estado.

Máquina de estados del secreto
Un secreto nace ACTIVE. Pasa a CONSUMED al alcanzar max_views, a EXPIRED cuando vence, a DESTROYED_BY_ABUSE tras cinco passphrases erróneas y a DELETED_BY_OWNER cuando el dueño lo borra. Todos los estados distintos de ACTIVE son terminales y vacían el contenido en la misma transacción que provoca el cambio.
La fila terminal queda 30 días como tombstone (sin contenido) para auditoría y para mostrar el estado real al dueño. Después la borra el job de limpieza. Un secreto vencido pero todavía marcado ACTIVE (porque el job no corrió) se trata como no disponible en la lectura.
5. Criptografía y ciclo de vida del secreto
Cada secreto se cifra con su propia clave de datos (DEK), y esa clave se envuelve con una clave maestra versionada (KEK); leer un secreto lo consume y lo destruye en una sola transacción. Todo el código criptográfico vive en el módulo crypto, y ningún otro módulo toca javax.crypto directamente.
Token del link
El token son 32 bytes de SecureRandom codificados en base64url sin padding (43 caracteres). La base guarda solo el SHA-256 del token, de modo que el link no se puede recuperar ni siquiera con acceso a la base, y se muestra una única vez al crear.
Cifrado envelope
• DEK de 256 bits por secreto, generada al crear.
• Contenido cifrado con AES-256-GCM, nonce aleatorio de 96 bits y tag de 128 bits.
• AAD de cada cifrado: id del secreto, versión de clave y versión de formato, para que un ciphertext no pueda moverse a otra fila.
• La DEK se guarda envuelta con la KEK de la versión activa.
• El puerto KeyProvider expone wrap y unwrap por versión. El adaptador del MVP lee las KEK desde variables de entorno o un archivo montado; un adaptador de KMS sobre LocalStack queda como extensión.
Passphrase opcional
La passphrase (8 a 128 caracteres) pasa por Argon2id con sal de 16 bytes por secreto y produce una clave que envuelve la DEK antes de que la KEK la envuelva. No se guarda ningún hash de la passphrase: una passphrase errónea se detecta porque falla el tag de GCM. Se usa Argon2 directo y no PasswordEncoder, porque este devuelve un hash codificado y no bytes de clave.
Protocolo de revelado
1. GET /s/{token} muestra una página intermedia que no consume nada. Esto evita que los previews de links de chats y mails (Slack, Teams, antivirus) quemen el secreto.
2. POST /s/{token}/reveal abre una transacción.
3. Se verifican rate limits, modo restringido y passphrase si corresponde.
4. Se bloquea la fila (FOR UPDATE o equivalente) y se comprueba que sigue ACTIVE, no vencida y con views menor que max_views.
5. Se descifra, se incrementa views y, si llegó al máximo, se vacía el contenido, todo en la misma transacción.
6. Se emiten los eventos (SecretRevealed y, si corresponde, SecretConsumed) y se responde con Cache-Control: no-store.
Los tres primeros controles pueden terminar la operación sin consumir nada; solo el cuarto paso cambia el estado del secreto.
La garantía exigida es exactamente-una-vez bajo concurrencia: con N pedidos simultáneos sobre un secreto de una lectura, uno recibe el contenido y los demás reciben no disponible. El mecanismo concreto (lock de fila o sentencia atómica) se decide al implementar y se verifica con un test de concurrencia. No se usa Post/Redirect/Get porque el contenido no puede guardarse para una segunda carga; la respuesta se renderiza directamente desde el POST.
Resultados del dominio
La operación devuelve una interfaz sellada, y el controlador la resuelve con un switch exhaustivo. Agregar un caso nuevo rompe la compilación hasta que se maneje.

Destrucción y borrado real
Vaciar columnas no garantiza el borrado físico: quedan copias en WAL, backups y páginas sin reciclar. Lo que da un borrado efectivo es la rotación de claves: cuando una versión de KEK se retira y se descarta, todo residuo cifrado con ella queda ilegible. Por eso la política exige rotar la KEK de forma periódica y retirar cada versión vieja una vez que pasó el TTL máximo (sección 8).
Visibilidad para el dueño
El dueño ve estado, lecturas, vencimiento y los eventos del secreto. No ve el contenido ni el token, y no hay forma de recuperarlos.
6. Autenticación e identidad
La app no tiene passwords propios: el usuario entra con Google o Microsoft, la identidad se define por emisor y sujeto (nunca por email) y los factores fuertes los aportan los passkeys. Cuatro piezas lo sostienen: login OIDC, política de provisión y vinculación, sesiones gestionables y step-up.
Login OIDC
• Dos registros de cliente, google y microsoft, con authorization code más PKCE y los scopes openid profile email. El redirect URI es {baseUrl}/login/oauth2/code/{registrationId}. state y nonce los valida Spring Security.
• Google es OIDC estándar con descubrimiento por issuer.
• Microsoft (Entra ID) con el endpoint common acepta cuentas personales y de trabajo, pero el issuer del id_token incluye el tenant del usuario y la validación por defecto contra el metadato de common falla. La solución es un JwtDecoderFactory<ClientRegistration> propio cuyo validador de issuer exige el patrón https://login.microsoftonline.com/{tid}/v2.0 con el tid tomado del propio token. Se prueba con tokens de varios tenants, incluido el de cuentas personales.
• La identidad es el par (issuer, sub). En Microsoft el issuer ya contiene el tenant, así que el par es único por tenant.
• Los claims name y email son solo datos de presentación. Nunca se usan para decidir quién es el usuario.
• Después del login solo se redirige a rutas internas relativas de una lista permitida (sin open redirect).
• El logout es POST /logout con CSRF e invalida la sesión local; no cierra la sesión en el proveedor.
Política de provisión (qué pasa al iniciar sesión)
El email de Google viene con email_verified; el de Microsoft no se puede dar por verificado, y confiar en él es la vulnerabilidad conocida como nOAuth. Por eso la política es explícita:
1. Si (issuer, sub) ya existe, se entra a ese usuario. Un usuario DISABLED es rechazado; uno en PENDING_DELETION entra y ve la opción de cancelar el borrado.
2. Si no existe y su email verificado coincide con el de un usuario existente, no se crea ni se fusiona nada. Se muestra una página que indica entrar con el proveedor original y vincular desde Seguridad.
3. Si no existe y no hay colisión, se crea el usuario y su primera identidad.
Un email sin verificar nunca cuenta para la colisión ni recibe notificaciones. Esto evita tanto la toma de cuenta como el bloqueo previo de un email ajeno.
Vinculación y desvinculación
• Solo se vincula desde una sesión autenticada y con step-up, iniciando un flujo OIDC marcado como link.
• Si el (issuer, sub) ya pertenece a otro usuario, se rechaza y se emite un evento.
• Desvincular exige step-up y no se permite quitar la última identidad.
Sesiones
• Spring Session JDBC. Cookie HttpOnly, Secure fuera de desarrollo, SameSite=Lax (con Strict se rompería el regreso del proveedor) y prefijo __Host- en producción.
• Fijación de sesión: se migra el id al autenticar.
• Vencimiento por inactividad de 30 minutos y absoluto de 12 horas, este último aplicado por un filtro que compara la hora de creación.
• Cada sesión tiene una fila en user_session_meta con IP truncada, resumen del user agent, métodos de autenticación usados y hora de la última autenticación fuerte.
• La UI muestra el id opaco de la fila de metadatos, nunca el id de sesión real. Revocar borra la sesión y su fila, y el próximo request de esa sesión se trata como anónimo.
• Un usuario solo puede revocar sus propias sesiones; revocar todas las demás exige step-up.
Passkeys (WebAuthn)
El passkey es segundo factor y credencial de step-up; en el MVP no es el login principal.
• Parámetros: RP ID igual al dominio (localhost en desarrollo), lista de orígenes permitidos, verificación de usuario requerida y attestation none. Se guardan credential id, clave pública, contador, transportes y etiqueta.
• Si el usuario no tiene ningún passkey activo, el primero se registra en estado PENDING_ACTIVATION y se activa a las 24 horas, con aviso por email si hay email verificado y posibilidad de cancelarlo desde otra sesión. Esto frena a un atacante que robó una sesión y quiere registrar su propio passkey.
• Si ya existe uno activo, agregar otro exige una aserción con el activo y queda activo al instante.
• Quitar el último passkey exige una aserción con él.
• Si el contador retrocede (y no es el caso 0 constante de los passkeys sincronizados), se marca la credencial como sospechosa y se emite un evento.
• La verificación WebAuthn usa el soporte nativo de Spring Security; hay que confirmar en la documentación de la versión exacta qué librería exige (webauthn4j).
Step-up para acciones sensibles
Acciones sensibles: vincular o desvincular identidades, agregar o quitar passkeys, revocar todas las otras sesiones, ver el historial completo de seguridad, borrar la cuenta, borrar todos los secretos y todo el panel de administración.
• Se exige un factor fuerte con antigüedad menor a 10 minutos.
• Si el usuario tiene un passkey activo, el factor fuerte es una aserción. Si no, es una reautenticación con el proveedor (prompt=login más max_age).
• Los claims acr y amr del proveedor no se usan para decidir; solo cuenta lo que la app verificó.
• Se apoya en el soporte de flujo MFA de Spring Security 7; la API exacta se confirma contra la versión usada al implementar.
Roles
Hay USER y ADMIN. ADMIN sale de una lista de identidades (issuer, sub) en configuración y nunca de claims del token.

Entrada, salida y errores
• La salida se escapa siempre con th:text; th:utext está prohibido por regla de arquitectura. El secreto se renderiza dentro de <pre> y se copia con textContent.
• Los tamaños se limitan en el servidor (formulario máximo de 70 KiB, secreto de 64 KiB, etiqueta de 80 caracteres).
• Hay una sola página de error y no se exponen trazas ni mensajes internos.
• Nunca se registran tokens, contenido, passphrases, ciphertext ni los headers Cookie y Authorization. De un token solo se loguean los primeros 8 caracteres de su hash. Un test canario falla el build si un valor secreto aparece en los logs.

8. Trabajo de fondo: jobs, eventos y notificaciones
Siete jobs y un flujo de eventos mantienen el sistema en regla sin intervención, y ninguno es necesario para la corrección de la lectura ni de la expiración. Los jobs usan @Scheduled con ShedLock (para que una sola instancia corra cada uno), se ejecutan sobre virtual threads y comparten las mismas reglas.
Reglas comunes de los jobs
• Idempotentes: correrlos dos veces seguidas no cambia el resultado.
• Por lotes de 500 filas con SKIP LOCKED para convivir con lecturas concurrentes.
• Cada ejecución escribe una fila en job_run y publica métricas.
• Todo el tiempo sale del Clock inyectado.
• Cada job expone un método run() invocable desde los tests; el scheduler está desactivado en el perfil de test.
• Un error en un lote se cuenta, se registra sin datos sensibles y no detiene los siguientes lotes ni la próxima ejecución.

9. Interfaz SSR: pantallas, rutas y UX
La interfaz es una app renderizada en servidor con dirección visual de herramienta de seguridad (sobria, con buen contraste y modo claro y oscuro), y todo flujo crítico funciona sin JavaScript salvo copiar al portapapeles y las ceremonias de passkey. htmx se usa solo para actualizar fragmentos: listas de sesiones, passkeys y secretos, y confirmaciones.
Principios de UI
• Thymeleaf con fragmentos reutilizables: layout, mensajes flash, estados vacíos, confirmaciones con <dialog> nativo.
• Tailwind compilado en el build con el CLI standalone; recursos propios con hash de contenido en el nombre y cache inmutable. Sin CDN ni recursos externos.
• Español por defecto e inglés disponible desde el inicio, con MessageSource; la elección se guarda en app_user.locale o en la cabecera Accept-Language para anónimos.
• Accesibilidad nivel AA: foco visible, labels en todos los campos, respeta prefers-color-scheme y prefers-reduced-motion.
• Un solo patrón de error: mensaje claro, sin detalles técnicos y con código de referencia (el request_id).
Reglas de UX de los secretos
• Tras crear, el link aparece en una pantalla única con el aviso de que no se vuelve a mostrar, un botón de copiar y un enlace al detalle.
• La pantalla intermedia del link explica qué va a pasar (se revela una vez y se destruye) antes del botón de revelar.
• El contenido se muestra en un bloque monoespaciado con botones de copiar y de ocultar. Nada se copia solo.
• Para anónimos, todos los fallos de disponibilidad usan el mismo mensaje.
• El dueño ve en su detalle el estado real, las lecturas y la línea de tiempo de eventos del secreto.

15. Prerrequisitos externos y entorno local
Antes del primer contrato de login hay que crear a mano una app OAuth en Google y otra en Microsoft Entra ID, porque ninguna de las dos se puede generar desde el código. Lo demás se levanta con un docker compose up.
Google
1. Crear un proyecto en Google Cloud Console.
2. Configurar la pantalla de consentimiento como externa. En modo de prueba solo entran los usuarios de prueba que agregues; para uso público hay que publicarla (verificá en la consola el estado actual de los requisitos para los scopes openid, email y profile).
3. Crear credenciales de tipo cliente OAuth para aplicación web.
4. Registrar los redirect URI de la tabla de abajo. Guardar el client id y el client secret.
Microsoft (Entra ID)
1. Registrar una aplicación en Microsoft Entra ID.
2. En tipos de cuenta admitidos, elegir cuentas de cualquier directorio y cuentas personales de Microsoft (coherente con D1).
3. Agregar una plataforma Web con los redirect URI de la tabla de abajo.
4. Crear un client secret en Certificates & secrets. Los secretos de cliente vencen: anotá la fecha y programá su renovación.
5. Permisos delegados openid, profile y email. Revisar los claims opcionales del token ID para email y tid (ver D2).

Reglas candidatas para CONSTITUTION.md
Surgen de los principios (sección 1) y de la seguridad transversal (sección 7), y son verificables de forma estática o por test.
1. Todo el código criptográfico vive en el módulo crypto; no hay javax.crypto fuera de él.
2. Nunca th:utext.
3. Nunca Instant.now() ni LocalDateTime.now(); solo el Clock inyectado.
4. No se registran tokens, contenido, passphrases, ciphertext ni los headers Cookie y Authorization.
5. Toda ruta nueva figura en la matriz de seguridad por rol.
6. Los módulos se comunican solo por eventos o puertos declarados, y ApplicationModules.verify() pasa.
7. No hay JPA ni Hibernate; el acceso a datos es SQL explícito con JdbcClient o Spring Data JDBC.
8. La identidad es siempre (issuer, sub); ninguna decisión de identidad usa el email ni los claims acr y amr.
9. Las respuestas a anónimos son uniformes: ningún mensaje distingue inexistente, vencido o consumido.
10. No se agrega una dependencia sin una nota ADR corta.
11. Ningún secreto ni credencial entra al repositorio.
12. security_event.details no contiene PII ni secretos.
16. Extensiones fuera del MVP
Hay ocho extensiones razonables, ordenadas de mayor a menor relación entre valor demostrativo y costo. Las tres primeras son las que más suman al portfolio sin deformar el producto.
1. Zero-knowledge del lado del cliente. La clave viaja en el fragmento de la URL (#), que el navegador nunca envía al servidor, y el cifrado AES-GCM ocurre en el navegador con WebCrypto. El servidor solo ve ciphertext. Costos: exige JavaScript, la CSP pasa a depender de un script propio y hay que redefinir cómo conviven la passphrase y el modo restringido.
2. Passkey como login principal para usuarios recurrentes, con los proveedores como alternativa y recuperación.
3. KeyProvider sobre KMS (LocalStack). Segundo adaptador del puerto ya definido, con la KEK fuera del proceso de la app.
4. API y CLI. POST /api/v1/secrets con tokens de acceso personales (guardados con hash, con alcance y vencimiento), usando el versionado de APIs de Spring Framework 7 y un cliente declarativo con @HttpServiceClient. Amplía bastante el alcance: conviene tratarlo como un proyecto aparte.
5. Roles y organizaciones desde Entra ID. Roles de aplicación o grupos para ADMIN y organizaciones por dominio de email verificado, con aislamiento entre ellas.
6. Webhooks firmados con HMAC para eventos como secreto leído, con protección contra SSRF en el envío.
7. Exportación firmada del log de auditoría.
8. Archivos adjuntos con cifrado por streaming, límites de tamaño y escaneo.
